# Architecture
Status: Canonical
Last reviewed: 2026-09-06

## System Overview
Ambit is a Tauri v2 desktop app with a React/TypeScript frontend and a Rust backend exposed through Tauri commands. Library assets and heavy metadata live in SQLite under Local AppData, lightweight app state lives in `library.json` under app-local data, and sensitive secrets such as the Gemini API key live in the OS keyring. Images remain the default asset type; videos use an explicit discriminator and bounded native probe through manual import, folder scans, and Live Watch.

## Major Subsystems

### Desktop Shell and Command Surface
Purpose: boot the Tauri app, register plugins, manage app-scoped state, and export Specta bindings.
Code: `src-tauri/src/lib.rs`, `src-tauri/src/main.rs`, `src/bindings.ts`
Interacts with: frontend services that call `commands.*`, Tauri plugins for SQL, filesystem, dialog, shell, and window state
Risks: command signature changes can break TypeScript callers; use `pnpm run bindings:generate` to regenerate `src/bindings.ts` and `pnpm run bindings:check` to detect drift
Related docs: `docs/progress.md#current-constraints`

### SQLite Data, Migrations, and Maintenance
Purpose: store image records, parsed metadata, facet caches, backups, reparsing state, and database maintenance behavior.
Code: `src-tauri/src/db/`
Interacts with: Rust scanner and metadata modules, TypeScript repo modules under `src/services/db/`, settings-backed folder sync
Risks: PRAGMA or migration changes affect startup, large-library performance, and data integrity
Related docs: `docs/refactor.md#persistence-boundary-cleanup`

### Metadata Extraction, Scanning, and Watcher Flows
Purpose: scan image and video files, extract metadata and workflows, resolve models, and watch library folders.
Code: `src-tauri/src/scanner/`, `src-tauri/src/metadata/`, `src-tauri/src/media.rs`, `src-tauri/src/watcher.rs`, `src-tauri/src/fs_commands.rs`, `src-tauri/src/security.rs`
Interacts with: frontend import, settings, maintenance, and viewer flows
Risks: parser heuristics and watcher behavior can create wrong metadata or miss library changes; external path handling must stay scoped and local
Related docs: `docs/manual/adding-folders.md`, `docs/manual/generator-integrations.md`, `docs/comfyui-support-workflow.md`

### Video Assets and Metadata
Purpose: probe local video candidates, generate static posters, scope playback/export, and preserve ComfyUI generation evidence.
Code: `src-tauri/src/media.rs`, `src-tauri/src/metadata/video.rs`, `src/services/videoService.ts`, `src/services/importService.ts`, `src/features/viewer/components/VideoViewer.tsx`
Interacts with: typed folder events, SQLite media columns, resource facets, metadata refresh, and shared viewer controls
Risks: admission does not guarantee runtime codec support; image-only operations must exclude videos; masked videos must not create a player before reveal
Related docs: `docs/manual/viewer-and-metadata.md`, `docs/plans/genai-video-library-support.md`

MP4, WebM, MOV, M4V, and MKV candidates are probed through the bundled Windows MediaInfo executable. Poster extraction uses the Windows media path; browser playback success or failure determines playback status. Grid and timeline use static posters, with a generic fallback when extraction fails. Video metadata has its own `VIDEO_PARSER_VERSION`, independent of image reparsing. A validated exact sibling `<stem>.workflow.json` takes precedence over embedded evidence; original evidence and conflicts are retained, and explicit user overrides survive refresh. Sidecar changes route back to the associated video through the import service. The active video plan records remaining owner acceptance and later assurance work separately from implemented behavior.

### Thumbnail Generation and Optimization
Purpose: generate cached WebP thumbnails, repair or upgrade thumbnail records in the background, expose maintenance controls, and throttle or cancel native work around foreground activity.
Code: `src-tauri/src/thumb/`, `src/services/thumbnailService.ts`, `src/hooks/useThumbnailQueue.ts`, `src/hooks/useThumbnailOps.ts`
Interacts with: SQLite image rows, app-local thumbnail storage, Activity Dock state, maintenance UI, collection thumbnail refresh, and generated Tauri bindings
Risks: background jobs write in batches and coordinate cancellation, retry backoff, cache-loss recovery, and foreground throttling; changes can create heavy disk or database work on large libraries
Related docs: `docs/manual/maintenance.md`, `docs/refactor.md#smart-thumbnail-optimization-and-thumbnail-maintenance-ownership`

Smart and Maintenance thumbnail repair share one native engine for source-root validation, generation, outcome persistence, cancellation, and diagnostics. Canonical required and upgradeable views use disjoint partial indexes and keyset ordering. Smart discovers those views incrementally without a startup count, respects failure backoff, and changes between normal and throttled orchestration around foreground activity. Maintenance keeps its exact scoped count and keyset pages, submits explicit image IDs at Fast priority, and bypasses failure backoff; Regenerate Selected additionally forces a real overwrite rather than accepting a cached file. One native job lease prevents Smart and Maintenance from processing concurrently. Manual leases carry a renderer-session owner so a replacement renderer can cancel and reclaim an abandoned operation after any active native batch settles.

The engine distinguishes three source outcomes. A readable source can be optimized or reused; an individually absent source is marked `is_missing` without deleting its cached thumbnail or database row; and a temporarily unavailable managed source root is skipped. It receives active monitored roots from the frontend, derives InvokeAI `outputs/images` roots from registered source identity, and caches unavailable roots before inspecting child files. Root probes are time-bounded, cancellation-aware, single-flight per root, and capped process-wide; a chunk containing absent children rechecks each affected root once before persistence so a drive disconnected during the run is deferred instead of marked missing. Mixed outcomes are staged and applied in one set-based transaction, with scope-cache triggers suppressed for the batch and each affected scope invalidated once. After an operation, image queries, library statistics, thumbnail facets, and collection thumbnails refresh once. Broken-reference repair, orphan cleanup, and developer-only database synchronization remain separate Maintenance tools.

Rescans preserve an active replacement thumbnail only after bounded WebP decoding validates it; missing or invalid replacements yield to the canonical thumbnail returned by the rescan.

Thumbnail repair batches record existing selective resource and collection dirty domains instead of an unknown full-rebuild cause. Retry diagnostics and excluded-scope outcomes do not invalidate projections. Existing unrelated full markers, generation checks, and transaction rollback remain authoritative.

### Startup Readiness and Diagnostics

Ordinary renderer diagnostics are validated and timestamped at native command receipt, then queued to the existing startup observer for JSONL and application-log delivery. The bounded in-memory queue has capacity for all admitted ordinary, terminal and repair records; its lock is never held during storage or logging. Receipt clocks remain independent of delayed persistence, and native teardown signals the observer without waiting for disk writes. A process terminated before the observer drains its tail still leaves incomplete evidence, not a guaranteed final record.

The nondefault `startup-sql-trace` Cargo feature provides diagnostic-only SQL-plugin boundaries in debug builds of the existing `com.ambit.dev` application. `pnpm run app:dev:sql-trace` creates a UUID-linked source/vendor manifest before compilation; normal `app:dev` remains tracing-disabled. The exact vendored SQL plugin 2.4.0 retains upstream default execution and registry/pool behavior, but the local Cargo patch changes dependency provenance even when disabled. Release trace builds are rejected.

Optional count tags correlate frontend settlement with native registry, binding, acquisition, retrieval and JSON-conversion intervals. Invalid/unavailable diagnostics never retry or prevent a business call. Plugin callbacks publish to fixed, unique-writer slots without acquiring observer storage; the existing observer independently drains them into a 64KiB allowance carved from ordinary journal capacity, preserving repair and terminal reserves. Pending/incomplete component timings remain null; reserved unpublished observations remain explicitly unknown. Admission stops at readiness/failure/180 seconds; already-admitted work can settle until teardown/deadline, with unmatched or incomplete evidence explicitly unknown. Acquisition includes opening/health checks; retrieval includes SQLite-worker scheduling, locking, execution and row transfer. These are not pure lock-wait/SQLite timings, and matching logical milestones do not prove pixels were displayed.

Debug startup reconciles migration history only in its active profile database; it does not enumerate or repair other development or production profiles. Release builds retain the existing compatible-profile migration repair behavior. This is a database-repair boundary, not a complete filesystem or keyring sandbox: copied catalogs must still have their operational source/cache paths redirected before testing.

Owner admission and privacy preparation remain fail-closed. Optional startup maintenance waits until the existing startup presentation has settled and the current owner/privacy scope has presented a successful first page, including an empty result. Same-scope filtering retains this admission so foreground image queries throttle Smart repair rather than repeatedly cancelling it; an owner/privacy admission change requires a new safe page. Thumbnail optimization waits 30 seconds after readiness, automatic metadata checking waits 3 seconds, and an idempotent native notification schedules the production backup check 120 seconds after readiness. Automatic metadata attempts remain single-flight across readiness changes. Manual maintenance controls retain their existing behavior.

The Statistics dashboard owns transient demand for keyword analysis. Closing it cancels further prompt batches, and keyword results are keyed by effective query/privacy/owner inputs and data revision. Browsing without Statistics does not launch the full prompt scan.

A current, fingerprinted InvokeAI All users snapshot may admit its saved aggregate view while ordinary source changes catch up through the existing timestamp-based startup sync. Its source fingerprint advances only after successful catch-up. Selected-owner source drift still reconciles before admission; missing or incompatible snapshots, unknown source state, schema/path upgrades and forced All users repair retain full reconciliation. Collection statistics traverse visible scoped collections and their indexed memberships instead of scanning the image library. These are query/admission changes, not schema or cache-format changes.

Owner visibility and board reconciliation acquire an immediate native write transaction before reading state, avoiding a deferred read-to-write upgrade failure when collection-cache writers overlap preparation. Each transaction entry has a scoped 2.5-second lock wait and restores the previous connection timeout afterward; this is not a deadline for query execution or all startup work. Typed local diagnostics identify preparation stages and classified failures, while native entry logs retain SQLite error codes and wait duration without user data. Startup catch-up forwards its actual outcome; a blocked or queued run is not a successful synchronization.

Windows identity normalization discovers distinct noncanonical source aliases through existing source indexes and updates only those exact aliases; already-canonical images, Removed rows and collection source IDs are not rewritten. Scope cache snapshot/restoration and alias-collision recovery remain unchanged. Fixed native substage timings separate normalization, cache snapshot/restoration and commit; bounded frontend diagnostics separate source opening/schema/owner summaries and gallery/count/statistic queries without changing their scheduling or logging user values.

Startup diagnostics use one random native launch ID and a dedicated JSONL under Local AppData `<active identifier>/logs/startup/`. Retention is limited to 20 feature-owned UUID-named files, each at most 256 KiB with reserved terminal capacity. Fixed classifications and timings exclude prompts, library paths, owner identities and raw errors. Native boot/page milestones survive missing renderer transport; renderer timestamps use `performance.now()` and native receipts use the process clock. A readiness summary distinguishes splash dismissal start, safe first page and readiness; initial Invoke catch-up completion is separate. Unrecorded milestones remain unrecorded. Graceful early exit is interrupted; a file without a terminal summary is incomplete/unclosed, not proof of a particular crash. Storage/transport failure does not block the app.

A separate typed heartbeat command updates native receipt state without journal writes or ordinary-event quota use. The renderer has one outstanding request at most, a two-second interval, no missed-message replay and a 120-second budget; readiness, fatal failure and page exit stop it. A dedicated native observer records pending-startup snapshots at 15/30/60/120 seconds with actual observer delay, last completed renderer phase, bounded outstanding phases and heartbeat age. A missing or >10-second-old heartbeat means renderer/transport responsiveness unknown, never a crash verdict. Page-load and Windows WebView2 ProcessFailed callbacks enqueue fixed atomic observations; disk writing happens off the WebView callback thread. Callback times and observer receipt times remain distinct. Windows registration owns COM handles only in UI-thread-local storage; teardown removes the handler directly on the registering thread at window destruction/process exit, records unavailable removal honestly, and does not alter canceled-close behavior. Process-failure observations remain available after logical readiness without rewriting its timing. The postmount 30-second warning only updates an existing loader; it cannot repair a stopped/non-painting WebView or prove visible pixels.

Process-failure observations retain the first nullable signed numeric exit code per fixed classification, read on the callback thread through the optional COM extension. Zero is a real code; null means unavailable. Descriptions, paths, frame details and dumps are never requested. A separate typed lifecycle command validates the active launch ID and enqueues first-occurrence close/drain/flush/exit stage labels through the same bounded atomic writer. Frontend sends are never awaited or replayed (at most nine per launch); native close/exit/window-destruction stages are recorded independently. These records use reserved capacity and do not modify readiness summaries or close ordering. They are best-effort receipt evidence, not a complete retry trace: final IPC can be lost during exit, and JSONL writer order does not establish callback order. Exit only signals/unparks the observer to finalize diagnostics; it never joins that worker or waits for disk. Process termination can truncate even a normal close's final summary, so absent tail evidence is unknown. Existing settings admission, drain, flush, shutdown optimization and exit semantics remain unchanged.

A self-hosted classic bootstrap runs before application modules; an independent small module connects its bounded events to native diagnostics. The static brand/status is visible without entrance animation or logo loading. Fatal script/runtime/provider errors show fixed plain-language fallback text and an available launch ID above the loader. Fifteen seconds without React mounting is a nonfatal stall indication. Neither a timer nor diagnostics dismisses the owner/privacy-protected opening. A WebView that never loads or stops executing cannot display a page-level fallback; native missing-renderer evidence is the limit of this phase.

Main frontend database callers share one initialization promise through URL resolution, loading and all six existing optional indexes. Failed opening can retry; optional index failure reports but leaves the loaded database usable. Invoke source opens share resolved-identity promises; failed opens and explicit retry/source replacement invalidate future lookups without closing in-flight handles. SQL results are not cached.

Collection storage preparation is separate from scoped metadata readiness and ordinary-count completion. It shares schema/legacy-store work without full counts; failed legacy import/marker writes preserve next-start retry data, and failed membership reads cannot authorize mock-collection deletion. Synchronization startup owns scoped row initialization after native owner preparation. Until the first safe gallery opens, ordinary membership counts remain explicitly pending; one store-coordinated read starts after the existing safe-gallery readiness signal, without waiting for catch-up. Unconfigured and trusted-offline starts use the same row-first load; unselected/error startup retains recovery gates. Generation/revision checks reject stale count results, and count-only updates do not invalidate image queries. Pending/failed counts do not infer zero from desktop membership placeholders; the active collection denominator can be unknown while filtered results remain known. Later authoritative runtime refreshes still await counts, even when readiness is withdrawn for an owner/privacy transition. Smart-count/thumbnail cache claims and generation-guarded hydration retain their existing ordering. No ordinary counts are persisted across launches; the existing owner-cache ready flag certifies its smart/thumbnail projection, not ordinary membership counts.

The startup-performance branch uses the exact pinned upstream SQL plugin 2.4.0. The local lock-release patch was withdrawn after failing its final synthetic performance gate; its source and provenance are archived in local build evidence. Upstream select/execute retain the registry read guard during database work, which can delay registration of another source. The actual MockRuntime test harness remains available; the future lock-release acceptance assertion is opt-in and is not an upstream guarantee.

The existing six frontend PRAGMAs remain inside the main database's shared initialization promise and are issued before the six existing optional indexes. Their failures are nonfatal and do not prevent index setup or make a loaded library unavailable. WAL is database-wide while the connection-local synchronous, busy-timeout, cache, temporary-store and mmap settings are not guaranteed on every pooled connection. Applying them to every physical connection was measured and rejected: representative generated-catalog latency regressed and peak process memory nearly doubled. Queries, indexes, schema, migrations, privacy/owner gates and startup scheduling remain unchanged. See the startup plan for retained evidence and the unresolved count-access and connection-policy boundaries.

Startup source-repair diagnostics reuse the typed startup command with fixed decision/stage/report payloads. The first pre-readiness repair retains invocation-local metric totals, maxima and call counts; five coarse stage records and one terminal report replace per-batch logging. Filesystem enumeration is nested within path resolution, while unattributed elapsed remains explicit. Native/plugin call measurements include transport and waiting, not just SQLite execution. A separate 8KiB repair allowance is taken from ordinary journal capacity, preserving the existing 32KiB terminal reserve and total file limit. Unknown fields and invalid aggregate shapes are rejected; unavailable fingerprints and missing reports remain unknown. These diagnostic descriptions never decide whether reconciliation runs. The renderer-stall warning threshold and repair aggregates are excluded from computational-work ranking. Reference sources replaced is an operation count, not a content-change count.

## Invariants
- SQLite is the source of truth for image records and heavy metadata. On Windows, the main library database lives in Local AppData, with Roaming AppData retained only as a legacy fallback during the public-beta transition. `library.json` should not become a second image store.
- Rust-exposed command and type changes should flow through Specta into `src/bindings.ts`; do not hand-maintain Rust-backed TypeScript mirrors.
- Generated binding updates are explicit: run `pnpm run bindings:generate`, then verify with `pnpm run bindings:check` or a broader gate that includes it.
- Filesystem access must remain local-only and within Tauri-registered or scoped paths.
- API keys are stored via Rust keyring commands, not persisted in `library.json`.
- Passive visual assets must be bundled locally. Network calls should be limited to the documented updater, Gemini, CivitAI, and user-clicked external-link paths.
- Large library browsing paths must remain virtualized and performance-conscious.
- Migration 80 generates regular and maintenance image-scope views from one SQL eligibility definition. Regular views retain their existing projections and planner freedom; narrow maintenance views require compact indexes so counts avoid metadata-heavy rows even after `ANALYZE`. The prompt-empty Boolean must be compared with `= 1`. Future visibility changes must rebuild all four views through the shared definition. Required-index failures surface as schema errors rather than falling back to heavy scans. Index creation has a one-time upgrade cost and relevant writes maintain the indexes.
- Removed listings exclude archival JSON blobs from IPC. SQLite extracts the positive prompt needed for privacy masking with the same sparse-metadata fallback as full row mapping; full ID lookups retain archival metadata for lifecycle and InvokeAI consumers. Maintenance hydrates only the currently opened Removed viewer item, with no retained detail cache after closing or navigating away.
- Gallery and timeline results for videos render static posters or a generic placeholder; they must not instantiate background video players.
- The bundled MediaInfo sidecar is invoked only by Rust-owned fixed arguments against canonical, authorized regular files from picker or monitored-folder scopes, with bounded output, timeout, cancellation, and single-process concurrency.
- Gallery and Maintenance reuse `ImageViewer` and `VideoViewer` according to the media discriminator. The viewers share sidebar, tab, metadata-field, collection-picker, and toolbar components while retaining image canvas and video playback behavior. Their navigation, deletion, recovery, and other context-dependent policies remain owned by their respective controllers.
- Removal is a recoverable database lifecycle: active images are transactionally tombstoned in `removed_images`, including their file hash and parser version, and restore reconstructs the active row plus supported memberships/resources in one transaction. Remove, restore, duplicate tombstoning, and final deletion share a process-wide coordinator so restore cannot race a source-file trash operation. Final deletion clears the tombstone only after OS-trash success (or when the source is already missing). Collection membership moves are likewise native transactions rather than frontend SQL sequences.
- Missing-source reconciliation is not deletion. It preserves the active database row and cached thumbnail so temporary storage outages are recoverable. User-requested removal is reversible and keeps its tombstone; user-requested final deletion OS-trashes the source and eligible thumbnail before clearing that tombstone.
- Full facet rebuilds populate a temporary staging table and swap into the live cache in a short transaction. Full and incremental refreshes share one coordinator so a queued targeted refresh cannot be overwritten by an older full-build snapshot.
- InvokeAI owner scope is a logical projection over one canonical Ambit database, not a separate database per user. Active images, Removed images, Invoke boards, and owner-aware Ambit collections carry an Invoke source identity; user-facing reads go through indexed scoped views driven by the atomic current-scope record. Ambit collections created in an owner view belong to that owner, collections created in `All users` are aggregate-only, and legacy unscoped collections remain shared until explicitly reassigned. Changing owners does not rewrite visibility across image rows. InvokeAI administrator status does not widen an owner projection; `All users` is the only aggregate scope. The reserved `system` owner is an ordinary owner projection, while discovery presents standard and intermediate image counts separately.
- InvokeAI board collections separate source facts from Ambit's effective projection. The source snapshot stores the authoritative board name, presence, and image names; local exclusions and additions store user organization; `collection_images` is the materialized result. Authoritative reconciliation replaces only source facts for boards present in the snapshot, follows upstream renames only when the displayed name still followed the prior source name, and retains absent boards as `Source unavailable`. Suppression hides a board collection without deleting source or override state. Reset clears local overlays and rematerializes the current source snapshot. Removed-image restore also rematerializes from current source facts and overlays, while sync refuses to resurrect tombstoned images or create active rows for missing source files.
- Facet and collection-derived caches have persistent per-scope snapshots. Mutations invalidate only scopes that can observe the changed Invoke owner (plus aggregate scopes), while local-library and global model changes invalidate every scope. A persisted dirty ledger distinguishes exact facet resources, whole facet types, collection summaries, and unknown full-rebuild causes. Dirty-ledger trigger writes use an explicit UPSERT conflict target because SQLite propagates a containing statement's conflict policy into trigger programs; shorthand `INSERT OR IGNORE` is not safe inside Ambit's image and board UPSERTs. A current snapshot activates immediately; a precisely dirty snapshot activates and repairs only its ledger entries; missing, legacy-dirty, or otherwise uncertain state falls back to a full rebuild. Cache builds use a generation handshake, so mutations during preparation prevent a partial projection from being committed as ready.
- An InvokeAI owner transition reserves synchronization until its target catch-up either succeeds or rolls back. Duplicate startup requests coalesce with the selected scope, same-scope startup callers share one active result, and Live Watch drains only after both the active run and owner transition have settled; unrelated callers cannot overwrite the selector's success decision. Enabled owner application refreshes the authoritative board catalog even for a current schema marker, so an owner-owned board remains visible with zero scoped members when all source members belong to other owners. A changed catch-up invalidates the image query; privacy-gated queries fetch after the target scope becomes ready instead of requiring a page reload. A required collection refresh that loses a normal newest-result-wins race retries until it applies a current scoped snapshot; genuine query failures still fail closed. Background Live Watch refreshes preserve the current settings and collection presentation: foreground preparation controls stay hidden, and collection summaries update without replacing established thumbnails or counts with pending placeholders.

## High-Risk Areas
- `src/App.tsx`: app shell integration point for selection, viewer, import, shortcuts, modals, and layout state.
- `src/contexts/SearchContext.tsx`: bridges React Query, SQL filter construction, collection refresh, and legacy store synchronization.
- `src-tauri/src/db/migrations/`: schema changes and backfills affect existing user libraries.
- `src-tauri/src/metadata/comfyui/`: parser heuristics are subtle and guarded by many Rust tests.
- `src-tauri/src/thumb/` and `src/hooks/useThumbnailQueue.ts`: native background work, SQLite updates, cancellation, and foreground throttling must stay coordinated.
- `src/services/TauriFsRepository.ts` and `src/stores/settingsStore.ts`: persistence behavior, settings migration, and folder scope registration.
